## Recap: the PYTHONUTF8 bug found by the previous agent (still relevant, unchanged)
On Windows, the detect-secrets Secret Keyword plugin scan is sensitive to PYTHONUTF8: without it,
Python's default text-mode file reads use the process locale codepage instead of UTF-8, which can
silently garble matches in UTF-8-heavy doc files (false negatives, not false positives). The
test's subprocess calls force PYTHONUTF8=1 via an explicit env dict regardless of the invoking
shell's ambient environment, so IT00-01 and ST00-12 are deterministic either way.

## Concerns for follow-up

- Windows PYTHONUTF8 note for local devs: contributors on Windows who run pre-commit or
  detect-secrets directly, outside this repo's own test suite, without PYTHONUTF8=1 set in their
  shell, may get silently reduced detect-secrets coverage (false negatives from codepage decoding,
  not false positives) on non-ASCII/UTF-8-heavy files. CI's own convention already sets
  PYTHONUTF8=1 (U00-59), and this card's tests force it internally for the same reason, but there
  is no README/CONTRIBUTING note yet telling a human running the hooks manually to do the same.
  Worth adding when impl 00's README/CONTRIBUTING docs are written (out of scope here).
- Shared git hooks point at this worktree's Python: a previous agent ran pre-commit install
  against the shared .git/hooks (shared across this worktree and possibly others, or the main
  checkout). The installed hook shells out via uv run / this worktree's .venv interpreter. Anyone
  committing from a different worktree or the main checkout now runs this worktree's hook chain
  against their own tree, which could be confusing if the worktrees diverge. Flagging for whoever
  coordinates worktree lifecycle; not something this card's scope covers fixing.
