Any failure from there on — `StoreBusy` / `SchemaViolation` from `write_current` (`:100`; on Windows `os.replace` raises PermissionError -> StoreBusy whenever CURRENT is held open), a kill at that point, or, after the switch, `StoreBusy` from `select_runs` / `list_jobs` or a per-file `SchemaViolation` inside the post `cleanup_builds` (`:104`) — leaves the build `promoted`, and `resolve_build` (`herness/model/_build_support.py:106-114`) only resumes `building` builds. Verified with a probe in a scratch copy (StoreBusy once from `write_current`):
  - full pipeline job: the retry ignores the saved state and starts a NEW build, re-running build/enrich/score/dq (with real enrichment, the full LLM cost again); the stranded build is later marked `retired` although it was never CURRENT.
  - `--from-stage promote` job (`{"stages":["promote"],"build_id":B}`): every retry fails with `ConfigError("build B is promoted")`; the gate-passed build can never be promoted. If the failure came after the switch (post-cleanup StoreBusy), the job reports failure although CURRENT already names B, and a full-pipeline retry promotes a second, new build.
  - CURRENT is never wrong (it stays on the old build or correctly names B; retire/retention clean up the stranded build), so not Critical — but it contradicts U02-104 Errors ("the job retries and resumes at `promote`") and the F02-02 crash-safety intent; the spec note at docs/impl/02-data-model.impl.md:2448 only records it.
  - Smallest fix: (a) `resolve_build`: also resume a build whose status is `promoted` when the only requested stage not yet done is `promote` (payload `stages == ["promote"]`, or a saved state whose `stages_done` holds every earlier requested stage), returning `done` = requested stages minus `promote`; (b) `stage_promote`: if `warehouse.read_current() == run.build_id` the switch already happened — skip the DQ re-run and `write_current`, run only `cleanup_builds(mode="post", ...)` (its rule 4 retires the stale previous) and log `model.build.promoted`; otherwise re-run DQ and call `promote_build` as today (`update_build_row(promoted)` is idempotent). Tests: integration probes with `write_current` raising StoreBusy once (full-pipeline retry keeps the same build_id with `durations_ms == ["promote"]`; `--from-stage promote` retry succeeds) and with StoreBusy from the post cleanup (retry completes without a second build). Replace the "open point" text of the U02-104 spec note with this resume rule and mention it under U02-98 step 3.
