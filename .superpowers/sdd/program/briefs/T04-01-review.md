### Issues

#### Important (Should Fix)

**I-1. `fetchall`/Arrow parity is broken for values nested in STRUCT, MAP or UNION.** This violates the U04-01 postcondition. Location: `herness/metrics/_encode.py:143-159`, and `:191-194` (the MAP pair conversion runs only at top level).

My probe (DuckDB 1.5.5) gave these results:

| Query | `fetchall` | Arrow |
|-------|------------|-------|
| `SELECT {'h': 5::HUGEINT}` | `{"h":5}` | `{"h":"5"}` |
| `SELECT {'u': 5::UHUGEINT}` | `{"u":5}` | `{"u":"5"}` |
| `SELECT {'m': MAP {'k': 1}}` | `{"m":{"k":1}}` | `{"m":[["k",1]]}` |
| `SELECT union_value(m := MAP {'k':1})` | `{"k":1}` | `[["k",1]]` |

- **Why it differs:** Arrow exports HUGEINT as `decimal128(38,0)`, and step 14 encodes a `Decimal` as a string.
- **Impact:** the build hashes one way and the harness (which hashes Arrow batches via `iter_batch_rows`) hashes the other. They then disagree on the same result, and the Verifier falls through to `rows_equivalent`. That also compares the nested text exactly, so it reports a mismatch.
- **Disclosure:** the HUGEINT-in-STRUCT and MAP-in-UNION cases are not disclosed in the report.
- **Spec status:** partly plan-mandated, because step 14 says "encode by Python type", which cannot tell Arrow's `Decimal` apart from `fetchall`'s `int`.
- **Fix, either of:**
  - (a) Recurse type-driven into STRUCT, MAP and UNION by parsing the member types from the type string. This is preferred, but `_encode.py` is already at its 280-line budget.
  - (b) Fail closed: raise `SchemaViolation` for a nested `Decimal` under an integer member type and for nested MAP pairs.

  In both cases, add the four probe queries to the UT04-01 parity test, and record the spec delta against step 14.

**I-2. `rows_equivalent` accepts inf against any finite value, and inf against -inf.** Location: `herness/metrics/evidence.py:405-411`.

- `abs(inf - 1.0) = inf <= 1e-9 + 1e-6 * inf = inf` is True. My probe confirmed `rows_equivalent([("v","DOUBLE")], [(inf,)], [(1.0,)])` → `True`, and the same for `inf` vs `-inf`.
- This is plan-mandated by the literal U04-07 formula. But the builder already special-cases non-finite values (NaN==NaN), and this is a tolerance hole in the Verifier check (TH04-06).
- **Fix:** if either value is non-finite, return `x == y or (isnan(x) and isnan(y))`.
- **Test:** add inf-vs-finite and inf-vs-(-inf) cases to UT04-11.
