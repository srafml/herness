#### Important (Should Fix)
- **Concern 2, plan-mandated gap, not this card's to fix**: `BuildSettings` default `memory_limit="75%"` makes `open_for_build` unusable with an unmodified default settings object on the pinned DuckDB 1.5.5. Verified independently with a standalone probe against this worktree's `.venv`: both `duckdb.connect(config={"memory_limit": "75%"})` and `SET memory_limit='75%'` raise `Parser Error: Unknown unit for memory: '%'`. `docs/impl/02-data-model.impl.md` nowhere describes a percent→bytes conversion for `memory_limit` (grepped the whole file); U02-34's algorithm (line 912 of the spec) says pass `cfg.memory_limit` through verbatim, so the builder's decision not to invent a conversion in this card is correct per the brief. `herness/store/warehouse.py:181-192` (`_reader_config`/`open_readonly`, T02-09) has the identical exposure for any caller that explicitly passes a percentage `memory_limit` — its default is `None` (not `"75%"`), so it isn't hit by default, but the acceptance regex `_MEMORY_LIMIT_RE` (warehouse.py:30) still accepts percentages that DuckDB itself rejects. This is a genuine, pre-existing spec/config gap spanning T02-01's `BuildSettings` default and both T02-09 and this card's write side; it needs a controller decision (fix the default in T02-01, or add percent→bytes conversion in a config-loading layer) — flagging here rather than blocking this card, since the card's own unit spec forbids inventing the conversion.

#### Minor (Nice to Have)
- **Concern 4**: `herness/store/_warehouse_rw.py:90-98` — if `SET GLOBAL TimeZone = 'UTC'` fails after a `create=True` connect, DuckDB has already created the file on disk before `con.close()` runs, so a caller retrying `open_for_build(..., create=True, ...)` next would hit the "already exists" `ConfigError` instead of a clean retry. Correctly flagged by the builder as reachable only via the monkeypatched `_SET_TZ` test path in practice (a literal `SET GLOBAL TimeZone = 'UTC'` should never fail); not fixed, acceptable to leave as documented.
- `herness/store/_warehouse_rw.py:109` catches bare `Exception` (`# noqa: BLE001`) when reading the previous `CURRENT` value. This is broad, but it is the literal instruction of U02-34's algorithm step 2 ("errors → previous `None`") and is exercised by `test_ut02_23_write_current_previous_read_error_is_none`; not a defect.
